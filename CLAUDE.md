# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

GrayMatter — a chess opening trainer and puzzle trainer, shipped as an Electron desktop app (Vite + React 19 + TypeScript renderer, CommonJS Electron main process). Three modes: **Openings** (drill your own PGN repertoires), **Puzzles** (drill from a local Lichess puzzle CSV), **Play** (casual game vs. a simple heuristic bot).

## Commands

- `npm run dev` — run Vite dev server + Electron together (main dev workflow; opens the actual app window)
- `npm run dev:web` — Vite only, in a browser (no `window.graymatter` API available, so file-backed features degrade — see below)
- `npm run build` — `tsc -b` (project references, no emit) then `vite build`
- `npm run preview` — preview the built web bundle
- `npm run package` — build then `electron-builder --win` (produces an NSIS installer under `release/`)

There is no test suite and no lint script configured. Type-checking via `tsc -b` (part of `npm run build`) is the only automated check.

## Architecture

### Process split

- `electron/main.cjs` — Electron main process. Owns all filesystem access and exposes it over `ipcMain.handle`. Resolves a fixed set of file paths under the hard-coded Google Drive folder `G:/My Drive/Tom/Chess/GrayMatter` (`GRAYMATTER_DIR` / `PATHS` constants; shared between the user's desktop and laptop via Drive sync): white/black repertoire PGNs, `TrainingStatus.json`, `settings.json`, the puzzle CSV, `PuzzleStatus.json`. Nothing in the renderer touches the filesystem directly.
- `electron/preload.cjs` — context-bridges `window.graymatter` (`getPaths`, `readTextFile`, `writeTextFile`, `fetchNextPuzzle`, `advancePuzzleCursor`, `fetchSurvivalSet`) into the renderer with `contextIsolation: true` / `nodeIntegration: false` / `sandbox: true`.
- `electron/puzzleStream.cjs` — streams the (~1 GB) Lichess puzzle CSV line-by-line rather than loading it into memory. Tracks a `nextByteOffset` cursor in `PuzzleStatus.json` and opens the stream at that offset, so each fetch only reads from the cursor to the next match regardless of file size or position; wraps around to the first data row when it runs off the end of the file. The header is read separately (`readCsvHeader`) to resolve column indices.
- `src/graymatter.d.ts` — the renderer-side type contract for `window.graymatter`; keep this in sync with `preload.cjs` any time the IPC surface changes (three places to update together: `main.cjs` handler, `preload.cjs` bridge, `graymatter.d.ts` types).

Renderer code always checks `window.graymatter` before using it, since `npm run dev:web` runs without Electron and that global won't exist — the affected pages show a "run this app in Electron" error state instead of crashing.

### Repertoire trie and cards (Openings mode)

This is the core data structure of the app, spread across these files:

- `src/pgnPaths.ts` — parses PGN text (via `@jackstenglein/pgn-parser`) into a flat list of SAN move sequences (one per line/variation). Handles the tricky part of PGN RAVs: distinguishing a variation that **replaces** the main move (alternate, e.g. `1.e4 (1...c5) e5`) from one that **continues after** it, by replaying both candidates through `chess.js` and seeing which one is legal. Also drops any path that's a strict prefix of a longer path in the same file, so an accidentally-short "stop" line doesn't shadow the real continuation.
- `src/moveTree.ts` — builds/walks the trie (`Node = { fen, moveFromPrevious, children }`) from those SAN paths; Explore walks it directly.
- `src/repertoireCards.ts` — `buildCardDeck(root, side)` folds the trie into a position graph keyed by `fenSig` (first 4 FEN fields; chess.js only writes an e.p. square when the capture is legal, so transpositions share a key). Each `PositionNode` holds the union of its book edges (keyed by UCI) and `reachPaths`, the routes written in the PGN (used only to open Explore from Progress). A breadth-first pass from the start gives each position its shortest distance (`dist`), its shortest-route predecessors (`incoming`) and a canonical route (the lexicographically smallest shortest route). A **card** is one trainee book move from one position (`id = "<fenSig> | <uci>"`, so the id also encodes the side); `depth` (trainee move number), `line` and `order` (cards sorted by canonical route, so branches stay together) all come from the canonical route. Opponent moves aren't cards. Drill reads only the graph, never `reachPaths`, so a normalized PGN (a transposition's continuation written once) and a denormalized one give the identical deck and Drill behaves the same. `pickSetupPath` walks `incoming` backwards from the card, so setup uses every move order into a transposition: uniformly random among the shortest routes that pass the fewest cards still in learning. Positions with two book moves for the trainee get two cards and a console warning.
- `src/srs.ts` — SM-2 with automatic pass/fail grading (`gradeCard`): learning steps 1 → 10 min, then 1 d; review passes go 6 d, then `interval × ease`; a lapse costs 0.2 ease (min 1.3), halves the interval and relearns through a 10 min step. `pickNextCard` takes due cards (most overdue first), then new cards (shallowest first, capped by `openingsNewPerDay` via each record's `introduced` date), then learning cards due within 20 min. `pickChainPath` picks a chain's next stop: a breadth-first walk from the position after the trainee's answer, through opponent replies and **practice** cards (review cards not yet due, which the trainee plays ungraded; `missPracticeCard` relearns a missed one with a halved interval but no ease change), to the nearest card to test (due, new within the daily cap and the chain's `CHAIN_MAX_NEW` = 3, or, only when a jump would pick one too, learning and due soon). It returns the first stop on that route; with nothing to test it practices down a random line. A learning card that isn't due, a new card past the cap, Max depth or a leaf ends the line, so the chain never replays a move still being learned.
- `src/trainingExport.ts` — `TrainingStatus.json` v4 (`keyKind: 'positionMove'`): `white`/`black` arrays of `ReviewRecord`s sorted by `due`, only for reviewed cards (`san` and `line` are for reading by eye). `attempts`/`correct` count graded showings for accuracy (counted in `DrillView.onCardAnswered`, not `gradeCard`), leaving out a new card's arrow intro and practice moves; older rows without them read as 0. `readSchedule(path)` is the shared read (missing file = empty schedule). Anything else (including the old v3 line-based file) reads as an empty schedule. `mergeSchedules` keeps the newer `lastReviewed` per card.

`OpeningsPage` (`src/openings.tsx`) loads both repertoires once (`LoadedRepertoires`) and shows one of three views, switched by an Explore | Drill | Progress control in each view's panel. Explore is the default every time the tab opens (not saved).

**Explore** (`src/openingExplorer.tsx`): `ExploreView` holds the chosen side (oriented at the bottom) and a SAN `path`; `ExploreChessboard` shows `walkToNode(root, path).fen` and draws an arrow for every child SAN (amber for the explored side's moves, blue-gray for the opponent's); hovering or focusing an opponent book-move button in the panel draws that move's arrow green (`SOLUTION_ARROW_COLOR`, as in Drill) and on top (`hoveredSan`). Nothing plays automatically: either side may move on its turn, a book move (matched with `repertoireSanForPlayed`) or a click in the panel's book-move list appends to `path`, and an off-book legal move gets the shared red wrong-move outline for `WRONG_MOVE_DISPLAY_MS` before the position returns. At a trie leaf no arrows are drawn and the last move's square gets the green `HINT_SQUARE_STYLE` outline. The panel shows the line as a `MoveList` (one move pair per row, scrolling, filling the free height), the book-move buttons below it (always reserving two rows), and Back (pops one move) / Reset (clears the path) pinned in `BoardPage`'s footer. Explore never touches the review schedule or disk.

**Drill** (`DrillView`): spaced repetition over cards. It builds a deck per side from the loaded repertoires and re-reads `TrainingStatus.json` every time it mounts (so the other client's reviews show up). `beginNextCard` picks a card for the Both/White/Black mode, filtered by `openingsTrainDepth` (the "Max depth" slider, fixed 3–20 range), and jumps to it: `CardChessboard` plays a `pickSetupPath` route out from the start position, one move every `MOVE_ANIMATION_MS`, then waits for the trainee. During that setup the panel already shows the finished line and the card ("Your move" / "New move"): `beginNextCard` sets `lineSans` in the same batch as the jump, and the board doesn't report history while `settingUpRef` is set. A Hint pressed during setup is applied once the card is up. Grading happens once per showing: a pass for the right move on the first try, a fail on the first wrong move or Hint. A card with no schedule record (`isNewCard`) is introduced instead: its answer is drawn as a green arrow (`SOLUTION_ARROW_COLOR`), Hint is disabled, wrong moves are taken back without grading, and playing the move counts as a pass (due in 10 min, so learn-ahead brings it back, arrow-free, later in the session). `onCardAnswered` updates the schedule and saves (`persistSchedule`, chained through a promise; it re-reads the file and merges before writing, except Reset, which replaces it). After a correct move the board asks `pickChainPath` for the chain's next stop and plays the opponent's reply at normal pace (the page counts new cards and visited positions per chain, reset on each jump; a practice stop shows a "Practice · not graded" banner); otherwise the move's square stays outlined in green (`HINT_SQUARE_STYLE`) for `CORRECT_MOVE_DISPLAY_MS` (2 s), then `onChainEnd` jumps to the next card (never the one just answered unless it's due). A different book move for the same position is taken back with no penalty ("Also in your book"). With nothing to study, the board shows the start position, locked, and a 30 s tick re-checks. The banner names each showing, fixed when the card is shown (`cardLabelFor`): Your move (a review), New move (arrow), Recall (a new card's arrow-free repeat, learning step 1), Retry (missed: relearning, or learning step 0), Practice. The panel shows Left this session (due reviews + cards still learning, whose minute-long steps all come back today, + new left today), Due / Learning / New today tiles, learned/total, session reviews, the current card's schedule, and Max depth / New cards per day sliders (both commit on release). Hint outlines the expected move's from-square in green; a legal wrong move is shown outlined in red for 2 s (`WRONG_MOVE_DISPLAY_MS`) and then taken back, without revealing the answer.

**Progress** (`src/openingProgress.tsx`, model in `src/progressTree.ts`): read-only. `buildProgressTree(deck)` builds the tree from the side's position graph, not the PGN: a position's continuation is drawn once, under its canonical route (`deck.canonical`: shortest, then alphabetically first), where the node is marked `transposed` if other move orders reach it too; every other move order into it is a leaf with `transposesTo` (the canonical route), so each card appears exactly once and normalized and denormalized PGNs draw the same tree (`subtreeCards` are the distinct card ids below). `layoutTree` is a hand-written left-to-right tidy layout in grid units (x = ply, one row per visible leaf, parents centered on their children) over the `expanded` set. `ProgressView` draws it as an SVG in `BoardPage`'s `wide` main area, with pan (drag) and zoom (wheel around the cursor). Trainee nodes: border by state (white untrained, amber learning, green review, red relearning), fill warmer with difficulty (ease, or accuracy once a card has 5+ attempts), a yellow dot when due, dimmed beyond Max depth; opponent moves are small gray pills. Click expands/collapses (a collapsed node shows +N and a learned/total bar; the +N turns yellow with a due dot when a due card is hidden below), double-click opens that line in Explore (`OpeningsPage`'s `exploreTarget` → `ExploreView` `initialSide`/`initialPath`), the ⇄ badge on a `transposesTo` leaf expands to and centers the continuation. Double-click opens Explore on the shortest written route to that position, since Explore walks the PGN as written. Hover shows the record (next review, interval, ease, passes/lapses, accuracy, dates). It opens on the side Drill trains (with Both, the side with more due once the schedule is read). The panel shows counts by state, accuracy, a 7-day due forecast and the 5 hardest moves (lowest ease, then lapses, then accuracy; click to reveal in the tree).

### Puzzles mode

`src/puzzles.tsx` (side panel: Practice/Survival segmented control, a side-to-move status banner, theme chips, then either the rating range plus a current-puzzle card with a Lichess link (Practice) or `SurvivalPanel`'s score/strikes/progress or game-over cards (Survival)) → IPC `fetchNextPuzzle` → `electron/puzzleStream.cjs` streams `lichess_db_puzzles.csv` starting at the saved byte offset, returns the first match (and the offset just past it) without moving the cursor, wrapping to line 0 if it reaches EOF without a match. The page moves the cursor (IPC `advancePuzzleCursor`) only when a Practice puzzle is solved or skipped with Next puzzle, so an unfinished puzzle comes back after a mode switch or app restart. `src/puzzleBoard.tsx` plays the puzzle's setup move automatically, then the trainee must match the CSV's expected UCI move at each of their turns (a wrong move that isn't checkmate is shown outlined in red for 2 s, then taken back); supports hint (green outline on the from-square) and "play solution" (auto-plays out the remaining line).

**Survival** (`puzzleMode: 'survival'`): Start run calls IPC `fetchSurvivalSet`, whose `collectSurvivalSet` makes one pass over the CSV from the saved cursor (wrapping back to it) and fills the rating buckets in `src/puzzleSurvival.ts` (`SURVIVAL_BUCKETS`, each `count` puzzles within ±`SURVIVAL_BUCKET_RADIUS` of `rating`; a puzzle goes to the nearest bucket with room), honoring the checked themes and ignoring the rating slider. The cursor is advanced past the line that filled the last bucket, so Practice keeps getting unseen puzzles too. The set is played in rating order; hint/play solution are unavailable. Because `onMiss` is passed, a wrong move is not taken back: it stays on the board with the red wrong-move outline, the board locks, and `onMiss` fires at once; the page holds `SURVIVAL_MISS_HOLD_MS` and moves to the next puzzle in the list. `SURVIVAL_MAX_MISSES` (3) misses end the run; the best score is saved to `puzzleSurvivalBest` as soon as it's beaten. Whenever no Survival puzzle is loaded (before a run, while collecting, after it) the board shows the starting position (non-interactive) and the status banner carries the Start run / Finding puzzles / Run over prompt; `justMissed` drives the red "Wrong move" banner during the hold. After a run the game-over card lists each missed puzzle as a button that reopens that missed puzzle for review: no `onMiss` (wrong moves are taken back as in Practice), no effect on the score, and solving it returns to the start-position board. `scanPuzzles` is the shared row iterator behind both `findNextPuzzleFromCsv` and `collectSurvivalSet`.

### Play mode

`src/play.tsx` (`PlayChessboard`) is a simple non-persisted vs-bot board — no repertoire, no puzzle file, nothing saved to disk. Its bot prefers captures (by lowest-value capturing piece), then checks, then a random legal move. The board reports a `PlayStatus` (turn / check / checkmate / draw plus the SAN move list) through `onStatusChange` after every position change, which drives the page's status banner and move list.

### UI shell and widget kit

`App.tsx` renders a left nav rail (mode buttons, version at the foot) beside the active page. Every page uses `BoardPage` from `src/ui/layout.tsx`: the board in `.board-slot`, sized from the window height in `src/index.css` (811px at the default 1321×859 window), and a side panel filling the rest; the panel body scrolls when it runs out of room, and `BoardPage`'s optional `footer` stays pinned below it (Drill puts Hint/Reset there). `wide` swaps the square board slot for a flexible main area beside a fixed 22.5rem panel (Progress). Panels are built from the kit rather than ad-hoc markup: `src/ui/layout.tsx` (`PanelHeader` with an ⓘ tooltip, `StatusBanner` — bold title then its own capitalized sentence, no separator dot — `Section`, `Card`, `StatTile`, `ProgressBar`, `StrikeMarker`, `SideMarker`, `ErrorNote`), `src/ui/moveList.tsx` (`MoveList`, the boxed move-pair list shared by Play and Explore), `src/ui/controls.tsx` (`Button` primary/secondary/ghost/danger, `SegmentedControl`, `Chip`, `ValueBadge`, `RangeSlider` / `DualRangeSlider`, which commit on the native `change` event), and `src/ui/icons.tsx`. Colors and fonts are Tailwind v4 `@theme` tokens in `src/index.css` (surfaces `bg` < `rail` < `panel` < `raised`, `line` borders, amber `accent`, `success`, `danger`; Geist / Geist Mono bundled via `@fontsource-variable`, since the app runs offline). Use the tokens and kit components for new UI instead of raw slate/amber classes.

### Shared board plumbing

All three board components (`CardChessboard`, `PuzzleChessboard`, `PlayChessboard`) duplicate the same `react-chessboard` wiring pattern: a `gameRef` holding a `chess.js` instance as the source of truth, `fen` state driving the rendered position, click-to-move and drag-to-move handlers that converge on one `attempt*Move` function, and square-highlight state for move options / last move / selection. `src/boardTheme.tsx` centralizes the shared visual chrome (`boardChrome`, `customPieces` — SVGs served from `public/staunty/`, `MOVE_ANIMATION_MS`) plus the hint/selection/wrong-move square outlines, `withSquareOutlines`, and `WRONG_MOVE_DISPLAY_MS`, and the drag look (no piece scaling; `dropSquareStyle` only sets a CSS variable that legal target squares read through `LEGAL_TARGET_STYLE`, so just a legal square under a dragged piece gets the amber outline — every board spreads `LEGAL_TARGET_STYLE` into its move-option squares), shared by the trainer and puzzle boards so their hint and wrong-move feedback match. When touching move-input logic, check whether the fix applies to all three boards, since the logic isn't factored into a shared hook.

### Settings

`src/settings.ts` defines `AppSettings` (`openingsTrainDepth`, `openingsTrainMode`, `openingsNewPerDay`, `puzzleThemes`, `puzzleRatingMin`, `puzzleRatingMax`, `puzzleMode`, `puzzleSurvivalBest`) with JSON parse/serialize + validation; fields added later fall back to their defaults when missing from an older file. `App.tsx` loads it via `window.graymatter.readTextFile` against `paths.settings` (falling back to `DEFAULT_SETTINGS` and rewriting the file if it's missing or invalid) and passes `settings` + an `onSettingsChange(patch)` callback, which saves immediately, to each page. There is no separate Settings page — each page shows its own relevant settings. `OpeningsPage` and `PuzzlesPage` are not rendered until settings have loaded, so they start with the saved values (and the first puzzle fetch uses the saved filters). Sliders save on release (native `change` event), not on every drag step.

### Versioning convention

`src/appVersion.ts` exports `APP_VERSION`, a hand-maintained `0.<n>-<ISO date>` string shown in the window's top-right corner (rendered once in `App.tsx`). Bump `<n>` and refresh the date when cutting a build — it's the on-screen way to confirm which build is running.
